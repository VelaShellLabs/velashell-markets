# 安全检测流水线

市场收的是**别人写的可执行代码**,所以这条流水线是整个系统里最该被认真对待的部分。
本文写清楚它拦什么、不拦什么、以及为什么这样取舍。

## 一、不变量(改代码前先读这三条)

1. **没通过检测的包绝不进正式桶。** 上传只写 `vpx-quarantine`,通过后才服务端复制进
   `vpx-public`,下载只对正式桶签预签名 URL(`PackageStorage.CreateDownloadUrl` 根本没有
   隔离桶的重载)。物理分桶意味着"未检测的包能被下载"需要**两处**同时出错才会发生 ——
   而一个 `IsPublished` 标记位只需要一处判断写错。
2. **引擎不可用 ≠ 干净。** ClamAV 连不上抛的是独立的 `ClamAvUnavailableException`,
   流水线据此**重排队**(至多三次),而不是放行。把"扫不了"和"扫过没事"合成一个 bool,
   迟早会写出"连不上就当干净"。
3. **拒收的包不立即删。** 留在隔离桶里到保留期(默认 30 天),既是复盘依据,也给作者申诉的余地。

## 二、四层静态检查

实现在 `VpxStaticInspector`,每层都可能直接判死。

### 第 1 层:容器

复用 `VelaShell.PluginSdk` 的 `VpxContainer` —— 与宿主装包**同一份实现**,
所以不存在"市场认、宿主不认"的缝。

| 检查 | 结论 |
| --- | --- |
| 魔数不是 `56 50 58 1A`(改后缀的 zip) | `VPX_FORMAT` Blocking |
| 头部 CRC / 载荷长度 / 截断 | `VPX_FORMAT` Blocking |
| 载荷 SHA-256 与头部不符(篡改) | `VPX_FORMAT` Blocking |
| 签名验签失败 | `VPX_SIGNATURE_INVALID` Blocking |
| 未签名 | `VPX_UNSIGNED` Info(当前允许) |

### 第 2 层:压缩包结构

| 检查 | 阈值 | 结论 |
| --- | --- | --- |
| 路径逃逸(`../`、绝对路径) | — | Blocking |
| **重名条目** | — | Blocking |
| 条目数 | > 10 000 | Blocking |
| 解压总量 | > 512 MB | Blocking |
| 单文件解压后大小 | > 128 MB | Blocking |
| 压缩比 | > 200:1 | Blocking(解压炸弹) |

重名条目值得单独说:不同解包器对"同名两份"的取舍不一致(有的取第一个,有的取最后一个),
这正是"检测时看到 A、安装时落地 B"的经典把戏,所以直接拒。

### 第 3 层:清单

走宿主同一套 `PluginManifestReader`,外加市场自己的三条:

- 清单里的 **id / 版本必须与本次上传声明的一致** —— 不一致就是"拿别人的 id 顶替上架"的形状;
- `apiLevel` 不得高于市场支持的上限(高了宿主也装不上,不如在门口说清楚);
- 清单声明的入口程序集必须真的在包里。

### 第 4 层:内容启发

**插件本来就是可执行代码,"包里有 dll"当然不是罪证。** 这一层的定位是"值不值得人看一眼":

| 内容 | 结论 | 说明 |
| --- | --- | --- |
| `.exe` `.com` `.scr` `.msi` `.hta` `.jar` `.lnk` … | Blocking | 插件目录里没有正当理由出现可直接运行的东西 |
| `.ps1` `.bat` `.sh` `.vbs` `.js` `.reg` `.so` `.dylib` | Warning → 人工复核 | 有正当用途,也是最常见的投递载体 |
| 原生(非托管)DLL | Warning | 意味着 P/Invoke 面 |
| 包内带 `VelaShell.PluginSdk.dll` / `Avalonia*.dll` | Warning | 装载器强制用宿主那份,带了要么是配置错,要么是想顶替宿主实现 |

把这一层调成动辄拦截,结果只会是审核形同虚设 —— 因为很快就没人看告警了。

## 三、签名与身份连续性

带签名的包会与该插件**已发布版本的公钥**比对。换钥不判死,只转人工(`SIGNATURE_KEY_ROTATED`
Warning):它可能是正常的密钥轮换,也可能是发布身份被劫持,这件事机器判不了。

插件 id 的归属由数据库保证:`Plugin` 文档的 `_id` **就是插件 id**,别人再传同 id 的包会撞主键;
上传端点另有显式的 owner 校验,给出可读的 403 而不是一个主键冲突。

## 四、裁决与状态机

```
Blocking 有 → Failed      → Rejected(留隔离区,保留期后清理)
Warning  有 → NeedsReview → 仍是 Quarantined,进审核台队列
都没有      → Passed      → 搬进正式桶 → Published
引擎故障    → 重试 3 次 → 仍失败 → Errored → Rejected(可重传)
```

审核员放行走的是**与自动放行同一个 `PublishAsync`** —— 两条路径分叉的话,迟早长出不一样的元数据。

## 五、目前不做的事

- **动态沙箱执行**:能发现静态看不出的东西,但工程量大、误报多、要额外的沙箱运行时。
  真要做,应当是独立的一次性容器 + 无网络 + 只观测行为,而不是塞进这条流水线。
- **依赖成分分析(SCA)**:识别插件捆绑的第三方库有无已知漏洞。值得做,排在沙箱之前。
- **人工复核的 SLA 与通知**:目前 `NeedsReview` 的包会一直等着,没有超时策略和邮件提醒。
